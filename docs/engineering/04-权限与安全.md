# 权限与安全

本文总结当前代码版本中的权限和安全设计，并列出维护时必须注意的事项。

## 1. 账号体系

当前代码使用邮箱和密码登录。注册后需要通过邮件完成邮箱验证，未验证用户不能作为当前登录用户使用。

密码使用 `scrypt` 哈希，不应也不需要保存明文密码。

## 2. Session

登录成功后，系统会写入 `ustc_tta_session` cookie。该 cookie：

- 使用 HMAC 签名防篡改。
- 设置 `httpOnly`，前端 JS 不能直接读取。
- 生产环境设置 `secure`。
- 设置 `sameSite: lax`。

维护注意事项：

- `AUTH_SECRET` 必须足够随机，不能泄露。
- 更换 `AUTH_SECRET` 会让所有旧登录态失效。
- 如果管理员重置用户密码或封禁用户，应确认旧登录态是否按当前代码预期失效。

## 3. 管理员权限

用户角色由 `User.role` 控制，取值包括普通用户和管理员。管理员后台入口为 `/admin`。

管理员后台包含：

- 邮箱二次验证。
- 信任设备。
- 用户封禁、删除、资料编辑、角色修改。
- 批量创建测试账号。
- 批量加入比赛。
- 网站开关。
- 审计日志查看。

维护注意事项：

- 管理员账号不要共享。
- 离任管理员应及时降权或封禁。
- 管理员邮箱必须可用，否则无法完成二次验证。
- `ADMIN_REAUTH_SECRET` 建议单独配置；如未配置，代码会回退使用 `AUTH_SECRET`。

## 4. CSRF 防护

项目包含 CSRF token 机制：

- `/api/csrf-token` 设置并返回 token。
- `CsrfFormInjector` 会向表单注入隐藏字段。
- Server Actions 和部分 API 会调用 `validateCsrfToken`。

维护注意事项：

- 新增写操作时应调用 `validateCsrfToken`。
- 不要为了省事跳过 CSRF 校验。
- 如果表单提交出现安全校验失败，优先检查 token 注入、cookie 和部署域名。

## 5. 中间件访问控制

`middleware.ts` 会：

- 跳过静态资源和 Next.js 内部资源。
- 放行登录、CSRF token、站点状态、关闭页和管理员页。
- 检查站点是否关闭。
- 对未登录用户跳转到 `/auth`。

注意：中间件只做入口层控制，真正的权限判断仍应放在 Server Actions 和服务端数据读取中。

## 6. Server Actions 权限

多数写操作会在服务端重新获取当前用户，并判断：

- 是否已登录。
- 是否为比赛创建者。
- 是否为管理员。
- 是否为对阵双方。
- 是否处于允许操作的比赛阶段。

维护时不要只在前端隐藏按钮。前端按钮隐藏只能改善体验，不能作为安全边界。

## 7. 敏感环境变量

以下变量属于敏感或半敏感配置：

- `DATABASE_URL`
- `DATABASE_URL_UNPOOLED`
- `AUTH_SECRET`
- `ADMIN_REAUTH_SECRET`
- `AZURE_COMMUNICATION_CONNECTION_STRING`
- `CLOUDINARY_API_KEY`
- `CLOUDINARY_API_SECRET`

要求：

- 不要提交 `.env`。
- 不要把真实值写入 README、docs、Issue、PR 或聊天记录。
- private repo 也不应保存真实密钥。
- 发现泄露后应立即轮换密钥和数据库密码。

## 8. 比赛双引擎安全边界

- 比赛写入先在事务中锁定 Match，然后校验 `engineVersion` 和快速/正式属性；
- V2 actor、role、engine、stage、override 和结算策略由服务端注入，不从客户端 FormData 接收；
- V2 adapter 会拒绝重复字段、File 值、未知字段和受保护字段；
- Legacy 入口使用反向 engine guard；不支持的 V2 赛制只能 fail-closed，不得回退到 Legacy 表。

封禁服务按 engine 分派并保持同一事务边界：Legacy 比赛执行原有参赛清理；V2 六种正式组合会关闭受影响的 ACTIVE Entry/成员并冲正报名结算。批量封禁先在同一 Match 内统一改变全部目标 Entry 状态，再处理共享 Fixture，避免双方同时被封禁时错误判胜。淘汰签表按“一方不可用则零结算弃权、双方不可用则 NO_CONTEST、有效一方遇终局空来源则 ADMIN_BYE”推进。对已结束比赛或非 ACTIVE 历史身份，只清理合法待确认更正，不改写历史 Entry、成员、报名结算、已确认赛果或 Match 状态；解除封禁也不会自动恢复参赛身份。

V2 基本信息编辑是独立的窄命令：只允许比赛创建者在报名期内、分组和 Fixture 尚未产生时修改名称、描述、地点、比赛时间和报名截止时间。命令在 Match/actor 行锁后重验账号、权限、engine 和生命周期，用 `updatedAt` 防止陈旧页面覆盖新值；新截止时间必须晚于当前时间且早于比赛时间。V2 创建、编辑和详情展示统一采用 `Asia/Shanghai`（北京时间），不信任浏览器时区决定权威时间；客户端也不能传入赛制、状态或权限覆盖。

V2 桌号/场地标签也是独立窄命令：六种组合的小组标签只能由比赛创建者或平台管理员维护，客户端只提交稳定 `groupKey`、完整 Fixture/version 快照和受限字符串数组；服务端验证发布拓扑与同组一致性后，在同一 Serializable 事务更新组内 Fixture、兼容投影和审计。淘汰赛标签按单个稳定 `fixtureId/version` 更新，并验证完整的签表发布元数据。已结束比赛只读展示标签，客户端不能直接提交 metadata。

## 9. 图片上传安全

头像上传当前包含：

- 文件大小限制。
- MIME 类型判断。
- 图片 magic bytes 校验。
- 上传到 Cloudinary。

维护注意事项：

- 不要放宽上传类型到任意文件。
- 不要直接信任用户提交的 URL。
- Cloudinary 密钥只能放在服务端环境变量中。

## 10. PDF 证明与身份信息

参赛证明功能会要求用户输入姓名和学号。代码中以哈希形式保存身份信息，用于之后验证输入是否一致。

维护注意事项：

- 不要在日志、文档或前端页面展示完整身份信息。
- 证明导出接口应保持登录和资格校验。
- 证明 POST 必须先按 Match engine 分派；V2 六种正式组合都在 Match-first Serializable 事务内使用 Entry、冻结 lineup、ResultRevision 和 Settlement 重新校验资格，不能回退到 Legacy Registration/MatchResult。只有当前有效成员且至少有一场真实 `PLAYED` 参赛证据才能新签发，FORFEIT 不算参赛证据。
- V2 身份与证明编号使用 `createMany(skipDuplicates)` 的无异常冲突路径；Serializable 快照无法观察并发行时必须回滚并从新事务有限重试，不能在 PostgreSQL 唯一约束异常后继续使用已中止的事务。
- 字体路径错误可能导致导出失败，但不应把服务器路径暴露给普通用户。

## 11. 审计日志

管理员关键操作会写入 `AuditLog`，包括动作、对象、操作者、IP、User-Agent 和 details。

维护注意事项：

- 不建议随意清理审计日志。
- 如需清理，应先导出备份并记录原因。
- 审计日志中可能含用户邮箱或对象标识，不应公开展示。

## 12. 当前安全限制与建议

当前代码已经有基础防护，但仍建议持续改进：

- 登录限流是进程内 Map，多实例部署时不共享，建议改为 Redis 或数据库限流。
- CSP 仍包含 `unsafe-inline` 和 `unsafe-eval`，后续可评估更严格策略。
- 管理后台高风险操作建议增加二次确认和更细粒度权限。
- 部署平台、数据库和第三方服务账号应启用强密码和多因素认证。

## 13. 新增功能时的安全检查清单

- 是否需要登录？
- 是否需要管理员或比赛创建者权限？
- 是否调用了 CSRF 校验？
- 是否会修改 ELO、积分、赛果或用户角色？
- 是否会处理上传文件？
- 是否会输出用户邮箱、姓名、学号等信息？
- 是否需要写入审计日志？
- 是否需要限制频率？
- 是否在事务内按 Match engine 分派，并对不支持的 V2 路径明确拒绝？
