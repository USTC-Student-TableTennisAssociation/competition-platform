# 正式比赛内核与历史归档

本文件描述当前实现。最终业务规则见 [重构后的比赛规则](../product/04-rebuild-contract.md)，发布步骤见 [部署说明](../operations/01-部署说明.md)。旧的双引擎过渡计划、双打名单永久不可变约束已撤销。

## 比赛身份与名单

正式比赛统一覆盖单打、双打、团体，以及纯小组、小组加淘汰两种赛制。新建默认使用 V2；`PAUSED` 只暂停新建。旧正式比赛通过精简归档页展示，不再存在旧报名、分组、报分和确认入口。

- `MatchEntry` 表示一个稳定的参赛方：单人、双打组合或团体队伍。更换成员不会改变 Entry、分组位置或已获赛事成绩。
- `MatchEntryMember` 记录名单版本、成员身份和有效期间。版本变更保留旧行；继续参赛者旧行标记 SUPERSEDED，被替换者旧行标记 REMOVED，并记录原因。
- `MatchTeam` / `MatchDoublesTeam` 及成员表保存组队目录和邀请关系。报名激活后与 Entry 对应；管理员换人时同步当前目录。历史对局根据自己的名单版本读取，不与当前目录强行比较。
- 单打不支持替换个人身份。用户不得同时属于本赛事多个有效参赛方；换入者必须邮箱已验证、未封禁，且未占用其他队伍的组队关系。

## 赛程与成绩

`MatchGroup` / `MatchGroupEntry` 保存已发布的小组位置及种子依据。`MatchFixture` 是每场比赛的事实来源，双方固定引用 Entry 和对应名单版本。`MatchFixtureLineupMember` 保存该场完整结算名单。

组织者创建赛事时设置小组赛和淘汰赛局制（3、5、7 局制）。发布对应阶段时将局制写入 Fixture；首次报分、确认和成绩更正均验证指定局制，页面不能自行更改。本期团体仍提交队伍总比分，不使用单场个人局数约束。

`startedAt` 通过“开始比赛”记录真实开打状态，Fixture 状态保持 READY 以允许后续报分。即使没有点击开始，只要存在任何报分修订记录，该场名单也受到保护。

`ResultRevision` 区分待确认、已确认、被替代、作废等状态。待确认更正不会替换仍生效的上一条已确认成绩。小组赛确认完毕后，资格排名与淘汰签表在一个事务内发布；签表按固定依赖推进，不重新抽签。

## 管理员换人

`application/roster-management.ts` 在可串行化事务内重新检查管理员身份、比赛状态、Entry 版本、完整名单和账号资格。提交必须有原因，写入审计记录。

换人只重新绑定满足以下全部条件的场次：SCHEDULED / READY、`startedAt = null`、没有任何 ResultRevision、没有行政裁定。已开始、已报分、已确认的场次保留旧名单与个人结算归属。

小组排名仍按稳定 Entry 汇总；校验旧名单时检查其在对应场次的有效性。晋级资格检查当前名单，新发布淘汰场次使用当前名单。已发布但尚未开打的淘汰场次也可换人；从已完成轮次推进时采用有效的后续名单。

## 中途退赛与弃权

普通管理退赛写入 WITHDRAWN；违规取消资格和封禁处理使用 DISQUALIFIED。两者保留已确认赛果与其结算。

正常退赛在任何变更前检查待确认报分（包括待确认更正），存在时返回需先核实的错误。剩余场次按弃权、双方无结果或轮空晋级推进。弃权影响赛事排名和晋级，不创建个人成绩结算事件，不增加个人积分、ELO、胜负或场次。报名奖励按原退报规则冲销。

## 结算与未来出场名单

`SettlementEvent` / `SettlementEffect` 保存结算来源、应用、冲正与每位成员的变更。个人汇总、积分流水和 ELO 流水是同一事务更新的查询结果；不能在重构迁移时再次计算它们。

团体本期按 Fixture 中整队名单结算。这份名单不能被解释成真实出场证据。将来增加实际出场统计时，应单独记录出场事实并为新成绩选择新的结算策略；旧 Fixture、事件与成员收益保持不变。

报名奖励延续现有口径：普通单打、双打每人最多 1 分；团体与管理员代报名不奖励。报名与胜场奖励合计每人每赛事最多 5 分。冲销不扣成负积分，未追回部分记入事件 metadata。管理员换入者不会获得被替换者此前个人成绩或报名奖励。

## 历史数据与共用表

归档迁移仅针对 LEGACY 且非快速约球的赛事：统一已结束状态，清理旧分组、邀请和不关联账本的未确认申报。异常未确认申报如果关联账本，保留原记录作为内部证据，归档和个人战绩页只展示已确认结果。

保留 `Match` 基本信息、已确认 `MatchResult`、历史报名及关联成员数据。`Registration`、`MatchResult` 和账本仍被快速约球或个人历史引用，因此保留共用表，不把旧赛果猜测转换为新 Fixture。旧参赛证明与报名 CSV 接口返回 410。

已移除旧正式比赛报名服务、分组工具、报分表单及读取时自动完赛逻辑。用户封禁对旧表的参与者清理仅允许快速约球；归档历史无论旧状态为何均不进入该流程。

## 权限与页面

普通视图优先显示报名入口、我的对局和待确认成绩。完整赛程与名单可展开；换人和退赛集中在赛事管理。管理员切换普通用户视图后，三种赛型统一隐藏额外管理操作。服务端授权仍使用数据库内重新读取的账号角色，不能信任客户端或显示模式。

边界严格解析 FormData、验证 CSRF、拒绝重复/未知业务字段，忽略 React 附带的 `$ACTION_` 路由元数据，使用稳定 ID 与乐观版本。换人搜索接口仅管理员可用，不缓存；各写事务重新检查状态与权限。

- `roster-management.integration.test.ts` 覆盖双打/团体的已确认、待确认、已开打、未开始四种名单保护状态，以及连续换人、小组资格、淘汰晋级和个人归属。
- `archive.integration.test.ts` 验证归档前后已确认历史、个人汇总、积分与 ELO 账本完全保留，快速约球独立，错误旧状态不触发封禁清理。
- 保留快速约球锁、管理员账号安全和迁移检查；旧正式写入测试已替换为入口关闭与归档断言。
